# Missing browser backends: local feasibility

Date: 2026-10-26. This is a read-only feasibility note for the ten deferred tools in `docs/browser-tool-contracts.json`. It does not enable any tool or change the installed extension, its permissions, Chrome policy, or native-host registration.

## Current evidence and host inventory

The pinned UiPath bridge is extension 23.10.1 / driver 23.4.55.39317. `docs/pinned-driver-audit.json` and `docs/EXTENSION-CAPABILITY-VERIFICATION.vi.md` show no verified vendor route for system clipboard, process launch, JavaScript/native dialogs, file picker, correlated downloads, OCR, CV, accessibility audits, or semantic search. Do not dispatch guessed content-message IDs. Existing UiPath adapter coverage remains the path for its current tools.

Locally checked on this machine:

- Windows 10 Pro build 19045, Chrome 155, Node 24.21, .NET, PowerShell 7, and Windows PowerShell 5.1 are installed.
- Windows PowerShell exposes `Windows.Media.Ocr.OcrEngine`. A read-only in-memory probe found `TryCreateFromUserProfileLanguages()` available and one installed recognizer language, `en-US`. No image or page content was supplied to that probe.
- The initial host inventory found no Tesseract, ImageMagick, OpenCV, Pillow, `sharp`, `tesseract.js`, `onnxruntime`, `axe-core`, or Ollama executable/service. The implementation subsequently pinned `@techstark/opencv-js@5.0.0-release.1`, `pngjs@7.0.0`, and `axe-core@4.14.0` as project dependencies. No Ollama executable/service or configured model is present. Puppeteer is present only outside the repository; it is not a project dependency and should not be relied on without pinning it.
- The existing native-host manifest allows only the installed UiPath extension origin. A companion extension requires its own explicit installation and a separate native-messaging host registration/manifest with its own `allowed_origins`. Do not add the companion origin to the UiPath host manifest. Neither registration was changed.
- No browser was launched, no live page was changed, the Windows clipboard was not read, and no page data was sent to a provider.

## WinRT OCR execution probe

The WinRT route was exercised on a self-generated, temporary image, not just type-checked. Windows PowerShell 5.1 ran with `-STA`, generated a white PNG containing `MCP TEST 123` using `System.Drawing`, then used `Windows.Storage.StorageFile.GetFileFromPathAsync` → `Windows.Graphics.Imaging.BitmapDecoder.CreateAsync` → `GetSoftwareBitmapAsync` → `Windows.Media.Ocr.OcrEngine.TryCreateFromUserProfileLanguages()` → `RecognizeAsync`. The local result was exactly `MCP TEST 123` with one available recognizer language (`en-US`). The temporary PNG was removed in `finally` and its absence under `%TEMP%` was checked after the process exited. This verifies a concrete local OCR command path and text output only; it does not validate screenshot capture, bounding-box mapping, other languages, or live browser integration.

The private `Windows-BrowserHelper.ps1` implementation was then exercised through its Node wrapper. A read-only capability call returned `platform=windows`, `clipboardText=true`, `ocr.available=true`, `languages=[en-US]`, and `maxImageDimension=10000`; this checked command/API availability and did not read or write clipboard data. The opt-in test generated a new `MCP TEST 123` image under `%TEMP%`, passed its bytes to the helper, and the helper decoded it through an in-memory WinRT stream. Full-image and cropped-image OCR both returned `MCP TEST 123`; crop results retained full screenshot pixel coordinates. The test removed its image and temporary directory. In the final combined focused run, all 16 Windows-helper tests passed, including the real synthetic OCR test. This evidence is for the private local helper only; no clipboard operation, companion registration, browser capture, or public tool integration was exercised.

## Focused backend implementation checks

The final combined focused Node run passed 43/43 tests with no skips: 17 Windows-helper tests (including real synthetic WinRT OCR), 7 semantic-client tests, 6 visual-matcher tests (including real pinned OpenCV match and constant-template rejection), 5 accessibility-ticket tests, and 8 launch-manager/helper tests. Both PowerShell helper scripts passed the local PowerShell parser. The launch helper also ran in Windows PowerShell 5.1 against a generated temporary directory, inspected the current Node process, and found an inert message-only Win32 window fixture using the `Chrome_MessageWindow` class and the unique temporary path as its title; both unlocked and locked branches returned the expected PID. The fixture and temporary directories were removed. No Chrome process, browser profile, or real user profile was created or launched. Semantic transport used only an ephemeral loopback mock server; no Ollama service or page data was contacted. Accessibility tests injected the typed isolated executor; they did not launch the companion extension.

The pinned OpenCV.js build does not expose its Emscripten heap buffer, so the visual worker can enforce the configured 64 MiB heap ceiling only when a build exposes it. For this pinned build it instead bounds each PNG at 4 MiB, both images together at 2.2 megapixels, and the match workspace at 2.2 million cells, rejecting larger work before decoding. The Node worker V8 limits do not cap WebAssembly/external-buffer RSS; no hard process RSS limit is claimed. The semantic client remains unavailable until an explicit local model is configured. Launch readiness remains unavailable until a safe `UIPATH_BROWSER_PROFILES` alias is configured, and a new browser remains `running_unpaired` with no connection/tab refs. Clipboard writes with malformed successful acknowledgements now return `dispatchState=unknown`; tests confirmed no retry and did not access the live clipboard.

## Bounded backend recommendations

| Deferred tool | Viable local backend | Honest initial scope / identity and side-effect limits |
|---|---|---|
| `system_clipboard` | Windows `Get-Clipboard` / `Set-Clipboard` from a small PowerShell helper in the interactive user session. | Text clipboard only at first; OS-global, not browser-tab scoped. Serialize reads/writes, bound text length, and report write acknowledgement/readback separately. A write replaces global clipboard content. No clipboard reads during discovery/capability checks. |
| `browser_ocr` | Built-in WinRT `Windows.Media.Ocr` operating on a bounded screenshot artifact, returning text plus line/word rectangles. | This host currently supports `en-US` only. Keep screenshot capture and OCR local; report installed/selected language and pixel coordinate space. Return an unavailable-language error rather than downloading models. |
| `browser_visual_find` | Companion-extension screenshot capture plus local Canvas pixel/template matching, or a pinned image-processing dependency if scale/rotation tolerant matching is required. | Start with same-scale templates and a bounded viewport; return confidence and all bounded candidates, with multiple matches reported as ambiguous. Screenshot is valid only for the exact active tab in its window; recheck tab identity before/after capture and invalidate results after viewport/navigation changes. Do not market pixel matching as general CV. |
| `browser_semantic_query` | Explicitly configured **local Ollama** model for natural-language DOM interpretation; no external default. The code can send a bounded DOM/AX snapshot to that configured loopback endpoint only. | Ollama and a model are absent on this host, so capability stays unavailable until the user configures a local model. Require an explicit model name, localhost-only URL, bounded snapshot/result, prompt-injection treatment of page text, and structured returned element references validated against the same live document. An explicit role/name AX-query mode may use Chrome's Accessibility domain, but must be labeled as AX matching rather than silently treated as LLM semantics. |
| `browser_accessibility_audit` | Bundle/pin `axe-core` locally in the companion extension and run it against the selected page document. | Return axe rule IDs, impact, target selectors, and incomplete/manual-review cases; do not claim complete WCAG conformance. Scope by the same tab/document identity; closed shadow DOM and hidden/unrendered states need explicit limits. No hosted audit service. |
| `browser_dialog` | Companion extension `chrome.debugger` attached to one resolved tab; arm `Page.javascriptDialogOpening` before the trigger and respond via `Page.handleJavaScriptDialog`. | Covers JavaScript `alert`, `confirm`, `prompt`, and `beforeunload`, not OS/browser chrome dialogs. Keep the watch/decision scoped to connection + tab + pending dialog and serialize the response control path so it cannot queue behind the blocked page action. The debugger permission is a prominent, non-optional extension permission. |
| `browser_file_picker` | Same exact-tab CDP session, resolving a real `input[type=file]` node and calling `DOM.setFileInputFiles` with explicitly supplied local paths. | This implements HTML file-input upload, not an arbitrary native picker or `showOpenFilePicker`. Validate existing regular files under caller-approved paths, node type, tab/document generation, and post-selection metadata; never synthesize `input.value`. |
| `browser_download` | Companion extension `chrome.downloads.download()` for an explicit URL, retaining the returned download ID and watching `onChanged` until `complete` or `interrupted`. | Own only the ID created for the request. `DownloadItem` exposes URL/final URL/referrer/start time/state/filename but no `tabId`; therefore do not attribute an arbitrary click-origin download to a tab by timing alone. A wait/watch for page-triggered downloads must require a pre-armed unique correlation rule or return ambiguous. `downloads` permission is required. |
| `browser_press_keys` | Target-bound CDP `Input.dispatchKeyEvent` sequence (`rawKeyDown`/`keyDown`, optional `char`, balanced `keyUp`) over the companion extension debugger session. | Browser-dispatched events to one tab, not physical/global keyboard input or guaranteed OS shortcuts. Map public `tabRef` to the companion's Chrome `tabId` internally; require current document/focus evidence and release every pressed modifier/key in cleanup. Do not claim trusted-user-activation semantics from the protocol method name alone. |
| `browser_launch` | Spawn installed Chrome with a newly created, managed, non-default `--user-data-dir`, keep the exact child PID/pipe session, and expose only that owned instance. | Never reuse or attach to the user's default profile; stop only the process the backend created. Chrome 136+ ignores remote-debugging switches for the default data directory, so use an isolated profile (and preferably a process-bound debugging pipe). A new profile will not automatically have UiPath or the companion extension; keep capabilities separate until the extension is explicitly installed there. |

## Cross-backend identity and permission rules

The UiPath native bridge has its own client/context/tab-ref registries in `src/browser-runtime.mjs`. A companion extension has separate Chrome tab IDs and separate lifetimes, so it must establish an explicit connection handshake and maintain `tabRef -> chrome tabId` only server-side. Never accept a raw Chrome tab ID as an MCP target. Scope DOM node IDs, dialog watches, download refs, screenshots, and key events to the connection, tab, and current document generation; invalidate on detach, navigation, reload, tab close, or companion reconnect. Revalidate before state-changing CDP commands. For screenshots, verify that the exact target is still active in the specified window both before and after capture.

An auxiliary extension requires separate install/upgrade UI. Minimum Chrome permissions depend on the feature set but include `debugger`, `downloads`, and `nativeMessaging`; `debugger` cannot be requested as an optional permission and triggers a warning. The companion's stable extension origin must be explicitly registered in its dedicated native host's `allowed_origins`. Keep the UiPath host manifest and extension permissions unchanged.

## Readiness boundary

These are viable backends, not live browser acceptance results. Before exposure, implement real modules, declare each dependency/permission, wire the companion's exact connection/tab identity, and add focused offline contract tests. Live tests must use an isolated fixture/profile and must separately validate dialog ordering, exact file selection, download correlation, clipboard effects, screenshot identity, OCR language behavior, template confidence, local model handling, axe results, and key-up cleanup. Keep any backend unavailable until its required local dependency and identity checks are confirmed; do not fall back to mock successes.
